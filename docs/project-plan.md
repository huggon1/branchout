# Feedloom 项目规划

## 1. 项目定位

Feedloom 用来把来自不同社交平台的内容，组织成围绕用户 Topic 持续生长、可以追溯来源、能够按不同 Creator Profile 呈现的个性化 Feed。

项目采用“体验优先”的推进方式：

1. 先用假数据做出带应用界面和精简说明的产品 Pitch 讲解稿，确认完整流程和核心体验。
2. 从已经验证的页面和交互中提炼一套简单、稳定的模块协作契约。
3. 盘点并复用已有仓库、工具和平台能力，尽快跑通真实的端到端链路。
4. 完整链路成立后，再分别优化各模块的质量、稳定性和设计。

项目仓库名称为 Feedloom，GitHub 可见性为 Public。

## 2. 产品能力

Feedloom 第一阶段关注四组可以独立实验、又能通过契约协作的能力。

### 2.1 转发内容解析

用户在浏览社交平台时，可以把感兴趣的内容转发给 Feedloom。系统负责获取原始内容，识别文字、图片、视频、作者和来源信息，并保存一份可以回溯的内容记录。

用户可以浏览全部转发内容，查看解析状态，筛选平台和内容类型，打开详情，并把内容归入自己维护的 Topic。

第一版真实链路只需要证明一条内容能够稳定进入系统，不追求同时覆盖大量平台。Demo 可以通过假数据完整展示多平台和多媒体内容的理想体验。

### 2.2 基于 Topic 的定时收集

Topic 由用户创建和维护。每个 Topic 描述用户持续关注的方向，并配置收集范围、执行频率、启停状态和用于生成 Feed 的 Creator Profile。收集后按该配置连续整理并生成 Feed。

系统按照 Topic 定时运行已有的研究或采集能力，把结果保存为一次明确的收集运行。用户可以浏览 Topic、管理收集配置、查看历史运行、检查来源覆盖，并处理无结果或失败状态。

### 2.3 Creator Profile

用户可以指定一个创作者，由 Agent 分析其一组历史内容，形成可查看、可调整的 Creator Profile。

Profile 描述最终内容如何组织和表达，例如信息密度、叙述方式、内容结构和证据呈现方式。用户可以浏览已有 Profile、查看生成依据、查看表达规则，并预览同一份素材在不同 Profile 下的效果。

第一版 Profile 的目标是让用户能明显感受到切换前后的差异，而不是完整复刻某个创作者。

### 2.4 Feed 生成

Feed 生成器把 Topic 的收集结果和选定的 Creator Profile 组合成适合阅读的内容卡片。

每张 Feed 卡片需要让读者快速理解：

- 这是什么；
- 谁在使用或讨论它；
- 它带来了什么变化；
- 为什么值得继续了解；
- 原始信息来自哪里；
- 接下来可以尝试或继续探索什么。

用户可以浏览不同 Topic 的 Feed、通过 Topic 选择 Profile、生成和收藏内容，并查看 Agent 的生成过程与原始依据。

模型生成的文字不能替代原始证据。每张 Feed 卡片都必须保留到原始来源和对应收集运行的引用关系。

## 3. 总体开发顺序

### M0：仓库基础

完成公共仓库初始化、项目说明、开发约束、忽略规则和文档规范。

完成标准：

- GitHub 仓库名称和可见性已确认；
- README 能准确说明当前项目边界和状态；
- AGENTS.md 包含稳定的开发与验证约束；
- 仓库不包含密钥、登录态、真实私人内容或生成产物。

### M1：产品 Pitch 讲解稿

交付桌面网页形式的产品讲解稿，类似带应用界面设计的 PPT。每页以精简文字解释一个场景，配上完整界面示意，通过翻页理解流程；少量交互用于演示关键变化。

Demo 可以集中展示最终发生在手机、其他平台和后台的操作，也可以拆开最终自动连续发生的环节。演示页面不等于最终产品的信息架构。默认展示准备好的结果，不要求用户完成操作才能理解产品。

完成标准：

- 打开即有内容，翻页即可理解完整流程；
- 使用程序员学习与工作的示例：AI 新闻、GitHub Trending、AI 编程工具、产品构建、新产品趋势；
- 展示转发解析、Topic 推荐与人工选择、来源与频率配置、博主风格提取、收集、整理生成、Feed 阅读与依据；
- Topic 在配置时绑定 Profile，真实产品的收集到生成应连续完成；
- 解释为什么完整但杂乱的收集材料还需要整理成可读 Feed；
- 样例、模拟运行与概念界面明确标记，生成结论可追溯；
- 关键模拟支持运行阶段和必要的异常反馈；
- 不要求移动端适配、真实搜索、版本管理或完整后台管理；
- huggon1 确认讲解内容与界面效果后，才提交并合并 PR。

### M2：最小协作契约

根据网页 Demo 中已经验证的页面和交互，确定真实模块之间需要交换的最小数据。

第一版契约使用版本化 JSON Schema、代表性 fixtures 和契约测试表达，不提前建设复杂的服务治理、事件系统或通用工作流引擎。

建议先覆盖以下对象：

- SourceContent：平台原始内容和来源信息；
- TopicDefinition：用户定义的 Topic 及收集配置；
- CreatorProfile：Feed 的表达和组织规则；
- CollectionRun：一次收集任务的输入、状态和运行信息；
- CollectionResult：收集获得的内容及其来源；
- AgentRun：一次解析、Profile 生成或 Feed 生成过程；
- FeedEntry：最终展示给读者的内容；
- EvidenceRef：生成内容与原始证据之间的引用。

契约不仅要表达成功结果，也要能表达排队中、处理中、部分成功、无结果、鉴权失效、平台不可用和被用户取消。

完成标准：

- Demo 的假数据使用正式契约的字段形状；
- 每种核心对象都有至少一个代表性 fixture；
- 契约测试可以独立运行；
- 任一模块都能仅根据契约开发和测试；
- 契约中不存在具体平台实现泄漏到核心领域的字段；
- 跨页面跳转依赖稳定对象标识，而不是 Demo 组件内部状态。

### M3：真实链路

优先复用已有仓库和工具，把 Demo 中的假数据逐步替换为真实模块输出。

首轮真实平台范围为：

- 小红书作为必须验证的目标平台；
- 另选一个经能力盘点后确认、当前支持稳定的平台作为对照来源。

Last 30 Days 可以作为定时收集的候选适配器和能力基线，但 Feedloom 的核心契约不依赖它的内部数据结构。

完成标准：

- 一条真实内容能够进入 Feedloom 并形成可追溯记录；
- 用户可以把内容归入自己创建的 Topic；
- 至少一个 Topic 可以完成一次真实收集；
- 至少一个 Creator Profile 能影响真实 Feed 的生成；
- 最终页面可以查看从 Feed 到原始内容的完整依据；
- 失败不会伪装成空结果，页面能够表达真实运行状态。

### M4：分模块优化

完整链路跑通后，再分别提升：

- 平台解析成功率、媒体理解和失败恢复；
- 定时收集的召回率、相关性、去重和稳定性；
- Creator Profile 的准确度、可编辑性和版本管理；
- Feed 的可读性、个性化程度和证据表达；
- Agent 运行的可观察性、可取消性和结果比较；
- 页面信息层级、响应速度和异常状态。

每项优化都使用真实样例、可回放运行和人工对比进行验证。契约发生不兼容变更时，需要升级版本并同步更新 fixtures 和相关适配器。

## 4. Demo 的展示形式

### 4.1 角色与视觉

Demo 是产品流程讲解稿，采用桌面网页呈现。暖白与低饱和绿色、清晰排版和内容界面服务于阅读。左侧短文说明使用方式和原因，右侧展示应用界面，底部提供直接跳页入口。

不需要逐项复刻最终软件。手机分享入口可放进独立模拟页面；实际自动执行的收集与生成可拆成两页解释。主要交互是翻页，已准备的界面结果本身应足以说明产品。

### 4.2 七页讲解

1. **产品概念**：展示从跨平台关注到个人 Feed 的全貌。
2. **转发与理解**：模拟其他平台的转发入口，展示解析后的原文、作者、媒体与 Topic 推荐。Topic 由人决定，可以从推荐中选择。
3. **一次配置**：配置关注方向、来源平台、收集频率和 Profile。定时执行在 Demo 中只展示配置，手动按钮回放一次模拟运行。
4. **表达风格**：展示虚构博主历史样例、表达习惯与提取依据。两种预设风格分别强调实操叙述与简报结构。
5. **持续收集**：展示跨平台原始信息和来源覆盖，保留每次运行记录，支持成功、部分成功、无结果与失败的模拟场景。
6. **内容整理**：对照完整原始素材与编排方式，说明如何提取重点、组织叙述并保留限制和证据。可模拟逐阶段生成。
7. **阅读与依据**：展示写好的 Feed，读者能理解是什么、价值和下一步，并能展开原始内容和收集运行。

### 4.3 连贯流程与演示拆分

最终使用流程是：转发内容并发现 Topic，人工确定关注方向，配置来源、频率与 Profile，系统按计划收集、整理并生成 Feed。

博主风格提取是配置可复用 Profile 的配套能力，不是每次收集后必须手动完成的一步。生成使用本次收集时保存的 Profile，以免之后修改配置导致历史依据变化。

演示中可逐段展开，也可连续模拟收集与生成。页面之间的对象引用保持一致。无需实现搜索、通知、复杂管理、版本比较或恢复等辅助能力。

### 4.4 样例与模拟边界

- 平台内容、人物、项目和运行全部使用明确标记的虚构样例；
- 默认 Topic 围绕程序员学习与工作，结构可容纳其他主题；
- 同一对象使用稳定标识，Feed 保留原始来源与收集记录；
- 模拟解析、风格提取和生成回放确定阶段，使用预设规则与模板；
- 不展示模型内部思维，不声称接入真实平台或模型；
- 不生成无法追溯的性能数字、新闻事实或市场判断；
- 没有相关素材时展示无结果，不用其他主题内容冒充；
- 浏览器本地保存演示操作，可以恢复固定初始样例。

### 4.5 验收重点

- 不操作也能通过翻页看懂完整故事；
- 文字简短，界面本身承担主要展示；
- 能理解 Topic 配置如何驱动后续连续流程；
- 能理解博主风格提取与内容生成的关系；
- 能理解收集完整材料与生成可读 Feed 的不同目的；
- 原始素材、收集记录和生成结果可以相互追溯；
- 桌面界面层次清楚，核心演示按钮和异常反馈有效。

## 5. 已有能力复用

真实开发开始前，先制作一份能力盘点，至少记录：

- 能力名称和对应仓库；
- 当前维护状态；
- 可调用入口；
- 输入和输出；
- 鉴权与登录态要求；
- 是否支持稳定回放和自动测试；
- 适合通过依赖库、CLI、本地服务还是独立适配器接入；
- 距离 Feedloom 契约还缺少什么。

复用遵循以下原则：

- 不直接复制已有仓库的实现；
- 平台能力统一放在适配器边界后方；
- 使用防腐层把外部数据转换成 Feedloom 契约；
- 外部能力失败时保留原始错误和运行状态；
- 可以替换一个适配器而不改变核心对象和其他模块；
- 先跑通一个真实样例，再扩大平台和内容类型。

## 6. 数据与安全边界

- 登录态和 API 密钥只保存在本地配置或密钥系统中；
- 仓库、fixtures、日志和测试快照不得包含真实凭证；
- Public 仓库中的默认样例必须是虚构内容、获得许可的内容或明确可公开使用的内容；
- 抓取到的原始内容需要保留平台、链接、作者和抓取时间；
- 对无法获取、无法解析或无法确认来源的内容，系统需要明确显示失败，不能生成看似完整的结果；
- 公开代码和私有运行数据保持物理隔离。

## 7. 第一版质量判断

第一版不以支持的平台数量为成功标准，而以完整产品体验是否成立，以及一条真实链路是否可理解、可追溯、可回放为标准。

需要建立三组样例：

- Demo 样例：用于产品体验和页面回归；
- 契约样例：用于验证模块边界和异常状态；
- 真实样例：用于评估解析、收集、Profile 和 Feed 质量。

真实链路阶段，Feed 文案至少使用一批真实输入进行人工对比。Demo 使用虚构输入验证可读性与追溯关系。验收重点不是信息是否堆得足够多，而是读者能否快速理解，并愿意采取下一步行动。

## 8. 当前已确认事项

- 仓库名称：Feedloom；
- GitHub 可见性：Public；
- 第一阶段产物是桌面网页产品 Pitch 讲解稿，以短文、应用界面和少量关键交互解释完整流程；
- Demo 使用确定性的假数据呈现理想产品能力；
- Demo 包含独立页面、跨页面导航、Agent 生成和证据查看；
- 开发顺序：产品 Pitch 讲解稿、最小协作契约、真实链路、分模块优化；
- Topic 由用户创建和维护；
- 第一轮真实平台包含小红书和一个盘点后确认的稳定来源；
- 优先复用已有仓库、工具、Skills 和本地服务；
- 第一版以完整产品体验和端到端链路成立为主要目标。

## 9. 后续确认点

以下内容不在本规划中提前决定，分别在对应里程碑评审时确认：

- 最终产品的信息架构与视觉细节；
- 真实产品各页面必须支持的操作；
- 第一个对照平台；
- Creator Profile 的第一版字段；
- Feed 卡片的固定内容结构；
- 各已有仓库的具体复用方式；
- 真实系统所采用的技术栈；
- Public 仓库采用的开源许可证。
