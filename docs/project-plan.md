# Feedloom 项目规划

## 1. 项目定位

Feedloom 用来把来自不同社交平台的内容，组织成围绕用户 Topic 持续生长、可以追溯来源、能够按不同 Creator Profile 呈现的个性化 Feed。

项目采用“体验优先”的推进方式：

1. 先用假数据做出一个内容丰富、可以直接操作的完整网页应用 Demo，确认产品形态和整体使用体验。
2. 从已经验证的页面和交互中提炼一套简单、稳定的模块协作契约。
3. 盘点并复用已有仓库、工具和平台能力，尽快跑通真实的端到端链路。
4. 完整链路成立后，再分别优化各模块的质量、稳定性和设计。

项目仓库名称为 Feedloom，GitHub 可见性为 Public。

## 2. 产品能力

Feedloom 第一阶段关注四组可以独立实验、又能通过契约协作的能力。

### 2.1 转发内容解析

用户在浏览社交平台时，可以把感兴趣的内容转发给 Feedloom。系统负责获取原始内容，识别文字、图片、视频、作者和来源信息，并保存一份可以回溯的内容记录。

用户可以浏览全部转发内容，查看解析状态，筛选平台和内容类型，打开详情，并把内容归入自己维护的 Topic。

第一版真实链路只需要证明一条内容能够稳定进入系统，不追求同时覆盖大量平台。Demo 可以通过假数据完整展示多平台和多媒体内容的理想体验。

### 2.2 基于 Topic 的定时收集

Topic 由用户创建和维护。每个 Topic 描述用户持续关注的方向，并可以配置收集范围、执行频率和启停状态。

系统按照 Topic 定时运行已有的研究或采集能力，把结果保存为一次明确的收集运行。用户可以浏览 Topic、管理收集配置、查看历史运行、检查来源覆盖，并处理无结果或失败状态。

### 2.3 Creator Profile

用户可以指定一个创作者，由 Agent 分析其一组历史内容，形成可查看、可调整的 Creator Profile。

Profile 描述最终内容如何组织和表达，例如信息密度、叙述方式、内容结构和证据呈现方式。用户可以浏览已有 Profile、查看生成依据、编辑规则、比较版本，并预览同一份素材在不同 Profile 下的效果。

第一版 Profile 的目标是让用户能明显感受到切换前后的差异，而不是完整复刻某个创作者。

### 2.4 Feed 生成

Feed 生成器把 Topic 的收集结果和选定的 Creator Profile 组合成适合阅读的内容卡片。

每张 Feed 卡片需要让读者快速理解：

- 这是什么；
- 谁在使用或讨论它；
- 它带来了什么变化；
- 为什么值得继续了解；
- 原始信息来自哪里；
- 接下来可以尝试或继续探索什么。

用户可以浏览不同 Topic 的 Feed、切换 Profile、重新生成、比较版本、收藏内容，并查看 Agent 的生成过程与原始依据。

模型生成的文字不能替代原始证据。每张 Feed 卡片都必须保留到原始来源和对应收集运行的引用关系。

## 3. 总体开发顺序

### M0：仓库基础

完成公共仓库初始化、项目说明、开发约束、忽略规则和文档规范。

完成标准：

- GitHub 仓库名称和可见性已确认；
- README 能准确说明当前项目边界和状态；
- AGENTS.md 包含稳定的开发与验证约束；
- 仓库不包含密钥、登录态、真实私人内容或生成产物。

### M1：完整网页应用 Demo

使用准备好的假数据实现一个高完成度网页应用，完整展示各项能力如何独立使用以及如何协作。

这个 Demo 既用于验证产品体验，也是第一版产品形态的可操作原型。它不是简单的数据流图，也不是只能沿固定步骤前进的一次性演示。用户应当可以通过全局导航进入不同页面，浏览和管理各类对象，并在页面之间自然跳转。

Demo 不接入真实平台和真实模型。所有采集、解析和 Agent 生成过程都由确定性的假数据驱动，并在界面中明确标记为模拟运行。假数据可以展示理想状态下较丰富的能力，但不能伪装成已经完成的真实接入。

完成标准：

- 用户打开页面后不需要安装、配置或提供自己的数据；
- 应用包含完整导航、多页面结构和统一的视觉语言；
- 每个核心能力都有独立的浏览、管理和详情页面；
- 用户既可以自由探索，也可以完成一条从内容进入到 Feed 生成的完整体验；
- Agent 生成过程有清晰的输入、运行状态、输出、依据和版本；
- 页面同时覆盖成功、处理中、部分成功、无结果和失败状态；
- 用户可以在不同页面之间追踪同一个 Topic、内容、运行和 Feed；
- 用户可以一键重置全部 Demo 数据；
- 用户确认产品形态、信息架构和核心使用体验值得继续开发。

### M2：最小协作契约

根据网页 Demo 中已经验证的页面和交互，确定真实模块之间需要交换的最小数据。

第一版契约使用版本化 JSON Schema、代表性 fixtures 和契约测试表达，不提前建设复杂的服务治理、事件系统或通用工作流引擎。

建议先覆盖以下对象：

- SourceContent：平台原始内容和来源信息；
- TopicDefinition：用户定义的 Topic 及收集配置；
- CreatorProfile：Feed 的表达和组织规则；
- CollectionRun：一次收集任务的输入、状态和运行信息；
- CollectionResult：收集获得的内容及其来源；
- AgentRun：一次解析、Profile 生成或 Feed 生成过程；
- FeedEntry：最终展示给读者的内容；
- EvidenceRef：生成内容与原始证据之间的引用。

契约不仅要表达成功结果，也要能表达排队中、处理中、部分成功、无结果、鉴权失效、平台不可用和被用户取消。

完成标准：

- Demo 的假数据使用正式契约的字段形状；
- 每种核心对象都有至少一个代表性 fixture；
- 契约测试可以独立运行；
- 任一模块都能仅根据契约开发和测试；
- 契约中不存在具体平台实现泄漏到核心领域的字段；
- 跨页面跳转依赖稳定对象标识，而不是 Demo 组件内部状态。

### M3：真实链路

优先复用已有仓库和工具，把 Demo 中的假数据逐步替换为真实模块输出。

首轮真实平台范围为：

- 小红书作为必须验证的目标平台；
- 另选一个经能力盘点后确认、当前支持稳定的平台作为对照来源。

Last 30 Days 可以作为定时收集的候选适配器和能力基线，但 Feedloom 的核心契约不依赖它的内部数据结构。

完成标准：

- 一条真实内容能够进入 Feedloom 并形成可追溯记录；
- 用户可以把内容归入自己创建的 Topic；
- 至少一个 Topic 可以完成一次真实收集；
- 至少一个 Creator Profile 能影响真实 Feed 的生成；
- 最终页面可以查看从 Feed 到原始内容的完整依据；
- 失败不会伪装成空结果，页面能够表达真实运行状态。

### M4：分模块优化

完整链路跑通后，再分别提升：

- 平台解析成功率、媒体理解和失败恢复；
- 定时收集的召回率、相关性、去重和稳定性；
- Creator Profile 的准确度、可编辑性和版本管理；
- Feed 的可读性、个性化程度和证据表达；
- Agent 运行的可观察性、可取消性和结果比较；
- 页面信息层级、响应速度和异常状态。

每项优化都使用真实样例、可回放运行和人工对比进行验证。契约发生不兼容变更时，需要升级版本并同步更新 fixtures 和相关适配器。

## 4. Demo 的产品形态

### 4.1 Demo 的角色

Demo 要像一个已经可以使用的产品，而不是项目架构说明。

它需要同时承担三种作用：

- 体验原型：验证用户是否理解并喜欢完整使用流程；
- 产品沙盘：把理想能力放到同一个应用里，帮助确认功能边界和页面关系；
- 契约样板：通过跨页面共享的假数据，暴露模块真正需要交换的信息。

Demo 可以比第一轮真实接入更丰富。比如页面可以同时展示图片、短视频、评论、不同平台来源、多种 Profile 和多次 Agent 运行，即使真实链路最初只支持其中一小部分。

### 4.2 应用框架

Demo 采用多页面应用形态，并具有统一的应用外壳：

- 全局侧边栏，用于切换主要产品页面；
- 顶部上下文区域，用于显示当前 Topic、全局搜索、通知和 Demo 状态；
- 统一的对象详情模式，让 Topic、内容、Profile、运行和 Feed 可以互相跳转；
- 明确的“模拟数据”标记；
- 全局“重置 Demo”入口；
- 必要的加载、空状态、错误提示和操作反馈。

### 4.3 页面规划

#### 首页

首页让用户快速理解 Feedloom 当前正在做什么，并提供进入各模块的入口。

页面可以包含：

- 最近收到的内容；
- 正在运行和下一次计划运行的收集任务；
- 最近生成的 Feed；
- 常用 Topic 和 Creator Profile；
- 需要用户处理的失败或待确认状态；
- 一条可以立即开始的默认体验。

#### 内容库

内容库用于浏览和管理所有转发或收集到的原始内容。

页面可以包含：

- 按平台、Topic、作者、内容类型和解析状态筛选；
- 网格、列表和详情视图；
- 图片、短视频、正文和评论的组合预览；
- 解析状态和失败原因；
- 来源链接、抓取时间和证据元数据；
- 归入 Topic、收藏、忽略和重新解析等操作。

#### Topics

Topics 页面用于管理用户持续关注的方向。

页面可以包含：

- Topic 列表、搜索和状态筛选；
- Topic 详情、说明和当前覆盖来源；
- 收集频率、启停状态和下一次运行时间；
- 最近内容、历史运行和最新 Feed；
- 手动触发一次模拟收集；
- 从 Topic 跳转到相关内容和 Feed。

#### 收集任务

收集任务页面用于浏览和管理定时收集及其运行历史。

页面可以包含：

- 任务列表、计划时间和运行状态；
- 来源覆盖和每个来源的结果；
- 收集到的内容、去重结果和相关性摘要；
- 处理中、部分成功、无结果和失败示例；
- 运行详情、日志摘要、重试和取消等模拟操作；
- 从一次运行跳转到对应 Topic、内容和 Feed。

#### Creator Profiles

Creator Profiles 页面用于浏览、生成和管理表达风格。

页面可以包含：

- Profile 卡片、适用场景和最近使用时间；
- 创作者样例内容和分析依据；
- Agent 生成 Profile 的过程；
- Profile 的结构化规则和自然语言说明；
- 编辑、复制、重新生成和版本比较；
- 使用同一份素材进行多 Profile 对比预览。

#### Feed

Feed 页面是面向阅读者的最终体验。

页面可以包含：

- 按 Topic、Profile、时间和状态筛选；
- 信息层级清晰、内容丰富的 Feed 卡片；
- 图片、短视频封面、引用和关键评论；
- “为什么值得看”和“接下来可以做什么”；
- 证据抽屉，展示来源内容和生成依据；
- 收藏、标记已读、打开来源、重新生成和比较版本；
- 从 Feed 跳转到对应 Topic、Profile 和 Agent 运行。

#### Agent Runs

Agent Runs 页面集中展示由 Agent 完成的解析和生成工作。

页面可以包含：

- 运行类型、输入对象、使用的 Profile 和当前状态；
- 排队、分析、生成、校验和完成等阶段；
- Agent 使用了哪些来源和证据；
- 输出结果、版本差异和质量检查；
- 取消、重新运行、接受结果和恢复上一版本等模拟操作；
- 从运行记录跳转到输入和输出对象。

### 4.4 默认体验故事

Demo 内置一套跨页面保持一致的默认数据和体验故事：

1. 用户从首页点击“体验一次完整流程”。
2. 应用进入内容库，模拟收到一条小红书内容。
3. 用户查看解析后的文字、图片、作者和来源。
4. 用户把内容归入一个已有 Topic。
5. 用户进入 Topic 页面，查看相关内容和收集配置。
6. 用户触发一次模拟收集，并在收集任务页面观察运行过程。
7. 应用产生一组带不同来源和状态的收集结果。
8. 用户进入 Creator Profiles，选择或模拟生成一个 Profile。
9. 用户进入 Agent Runs，观察 Feed 生成过程和使用的证据。
10. 用户在 Feed 页面查看最终内容，并切换另一个 Profile 比较表达差异。
11. 用户打开证据抽屉，回到原始内容和收集运行。
12. 用户可以退出引导，自由浏览和管理 Demo 中的全部对象。

引导只负责帮助用户第一次理解产品，不限制之后的自由探索。

### 4.5 Agent 生成体验

Demo 中涉及 Agent 的功能不能只用一个“生成”按钮瞬间返回结果。

每次模拟 Agent 运行至少要表达：

- 使用什么作为输入；
- 当前执行到哪个阶段；
- 找到了哪些来源或样例；
- 生成了什么结构化结果；
- 进行了哪些质量检查；
- 输出与上一版本有什么差异；
- 用户可以接受、调整、重试还是恢复。

Agent 的内部思维过程不直接展示。页面展示的是可验证的执行阶段、工具结果、证据和产物。

### 4.6 假数据原则

假数据需要丰富、连贯并接近真实产品状态，而不是一组互不相关的占位文字。

- 同一个对象在所有页面中使用一致标识和内容；
- 每次模拟运行结果确定，可以稳定回归；
- 同时准备成功、处理中、部分成功、无结果和失败样例；
- Feed 中出现的事实必须能在假数据来源中找到依据；
- Profile 切换必须产生容易观察的内容差异；
- 平台、人物和内容使用虚构数据、获得许可的数据或明确可公开使用的数据；
- 所有模拟生成和模拟收集在界面中清楚标记；
- 重置后恢复到完全一致的初始状态。

### 4.7 Demo 验收问题

体验评审时重点回答：

- 应用是否像一个完整产品，而不是后台管理模板或数据流演示；
- 用户能否在不阅读额外说明的情况下开始操作；
- 不同页面的职责是否清楚，切换是否自然；
- 用户是否知道每个页面下一步可以做什么；
- 管理功能和阅读体验是否处于合适的平衡；
- 用户是否能区分原始内容、收集结果和 Agent 生成内容；
- 用户是否理解 Creator Profile 改变的是表达方式；
- Agent 生成过程是否让人感到可理解、可控制、可信；
- Feed 是否让人愿意继续阅读、收藏或打开来源；
- 证据入口是否足够明显，又不会干扰阅读；
- 哪些丰富能力值得进入第一条真实链路，哪些可以继续停留在 Demo。

## 5. 已有能力复用

真实开发开始前，先制作一份能力盘点，至少记录：

- 能力名称和对应仓库；
- 当前维护状态；
- 可调用入口；
- 输入和输出；
- 鉴权与登录态要求；
- 是否支持稳定回放和自动测试；
- 适合通过依赖库、CLI、本地服务还是独立适配器接入；
- 距离 Feedloom 契约还缺少什么。

复用遵循以下原则：

- 不直接复制已有仓库的实现；
- 平台能力统一放在适配器边界后方；
- 使用防腐层把外部数据转换成 Feedloom 契约；
- 外部能力失败时保留原始错误和运行状态；
- 可以替换一个适配器而不改变核心对象和其他模块；
- 先跑通一个真实样例，再扩大平台和内容类型。

## 6. 数据与安全边界

- 登录态和 API 密钥只保存在本地配置或密钥系统中；
- 仓库、fixtures、日志和测试快照不得包含真实凭证；
- Public 仓库中的默认样例必须是虚构内容、获得许可的内容或明确可公开使用的内容；
- 抓取到的原始内容需要保留平台、链接、作者和抓取时间；
- 对无法获取、无法解析或无法确认来源的内容，系统需要明确显示失败，不能生成看似完整的结果；
- 公开代码和私有运行数据保持物理隔离。

## 7. 第一版质量判断

第一版不以支持的平台数量为成功标准，而以完整产品体验是否成立，以及一条真实链路是否可理解、可追溯、可回放为标准。

需要建立三组样例：

- Demo 样例：用于产品体验和页面回归；
- 契约样例：用于验证模块边界和异常状态；
- 真实样例：用于评估解析、收集、Profile 和 Feed 质量。

Feed 文案至少使用一批真实输入进行人工对比。验收重点不是信息是否堆得足够多，而是读者能否快速理解，并愿意采取下一步行动。

## 8. 当前已确认事项

- 仓库名称：Feedloom；
- GitHub 可见性：Public；
- 第一阶段产物是内容丰富、具有多页面和管理能力的完整网页应用 Demo；
- Demo 使用确定性的假数据呈现理想产品能力；
- Demo 包含独立页面、跨页面导航、Agent 生成和证据查看；
- 开发顺序：完整网页应用 Demo、最小协作契约、真实链路、分模块优化；
- Topic 由用户创建和维护；
- 第一轮真实平台包含小红书和一个盘点后确认的稳定来源；
- 优先复用已有仓库、工具、Skills 和本地服务；
- 第一版以完整产品体验和端到端链路成立为主要目标。

## 9. 后续确认点

以下内容不在本规划中提前决定，分别在对应里程碑评审时确认：

- Demo 的视觉方向和具体信息架构；
